# WP-10: bus topology, partition cells and source control

Branch `feat/WP-10-bus-sources-cells`. Milestone A-M2. Owns
`internal/bus`, `internal/cell`, `internal/sources`, the
`source_controls` migration, the KV buckets, the routes `/v1/sources/*`,
`src.v1` and `schemas/source/*`. Depends on WP-1. Consumers: every
process.

Safety-relevant: a switch that fails closed hides aircraft; a switch
that does not propagate leaves a disabled source live. Reviewed
adversarially.

## What to build

### `internal/bus`

- Connection from per-process credentials (`NATS_URL`, `NATS_CREDS`),
  reconnect forever with jitter, startup retry 3× with backoff then
  start degraded with a warning (B-08; E-02 test: the process starts
  with NATS down and says so).
- Idempotent provisioning (`bus.Ensure(ctx)`, run by `api` at startup
  and tolerated by every process): streams `TRK` (mirror of `trk.v1.>`,
  1 h, memory or file per config), `ALRT` (7 d), `IDENT` (24 h), `CIS`
  (30 d), `INGEST` (work queue, 10 min), `TSW` (10 min); KV buckets
  `source_control`, `policy`, `cells`, `registry_version`,
  `zones_version`, `rid_receiver_keys` with history 8; max message size
  and bucket value limits set explicitly and checked by a test that
  writes past them (E-10).
- Typed helpers: `Subjects` (`Trk(cell3, cell5, id)`, `Man(...)`,
  `Alrt(kind, cell5, id)`, `Ident(id)`, `Cis(dataset)`, `Src(type,
  inst)`, `Ingest(cell3)`, `Tsw(table)`), publish with the `04 §2`
  envelope, pull-consumer wrappers with explicit ack and bounded
  pending, KV watch with the push-then-reread pattern.

### `internal/cell`

- A thin wrapper over core's `geodesy/cell` (additive in `uspace-core`
  v1.1.0, core WP-14; M35): `cell5` = 0.1° × 0.1°, `cell3` = 1° × 1°,
  names `c5:<lat_idx>:<lon_idx>` / `c3:<lat_idx>:<lon_idx>`, ring-1
  neighbours, bbox → cell set, antimeridian and pole handling, all
  judged and tested in core. This package adds only what is local:
  the subject-token form of a cell name, viewport → cell set with the
  margin, and the ownership map. If v1.1.0 is not tagged when this WP
  starts, the same grid with the same names lives here behind the same
  function signatures and is replaced by the import in a `build:`
  commit, with a test that the two agree on the vector points. No H3,
  no `Partitioner` interface (the grid is decided, Q-A3).
- `Ownership` from KV `cells`: cell3 → worker id; `api` writes it
  (`PUT /v1/cells` admin, audited); a worker owns the cells the map
  gives it and refuses to start with none unless `CELLS=all` (the demo).

### `internal/sources` (U-15)

- Migration `source_controls(source_type, instance_id NULL, enabled,
  reason, actor, changed_at, version bigint from a sequence, epoch
  text)`; `epoch` generated at table creation (migration) and stored in
  a one-row table so a restored database gets a new epoch (B-09).
- `Service.Switch(ctx, type, instance, enabled, reason, actor)`: in one
  transaction under `pg_advisory_lock('source_controls')`: the row, the
  `events` row, then the KV write of the whole `sources.State`; if the
  KV write fails the transaction rolls back and the API returns 503
  (B-09, SC-08 step 8); after commit, push on `ctl.sources`. Republish
  the state from the database every 60 s to repair a lost bucket.
- `Follower` wiring for every process: `core/sources.Follower` fed from
  the KV watch and the push subject, with no state everything enabled
  and a warning at startup that the switch state is unknown (SC-08 step
  8), counters exported; `Query(type, instance)` used by the adapters
  before accepting anything and by `detect` to clear alerts as
  `source_disabled` (WP-12).
- Status: every adapter publishes `src.v1.<type>.<instance>` every 2 s
  (`source/status/v1`: enabled, last seen, accepted, refused, queue,
  lag_s, `disabled_by`); `api` keeps the last status per instance for
  `GET /v1/sources` and the console shows `enabled`, `disabled by
  <who>`, `healthy`, `stale`, `lagging`, `never heard` (B-11, B-03).
- Routes `/v1/sources*` per plan §5, `admin` only; a `viewer` gets 403
  (SC-08 step 6, with the admin success beside it).

## Tests

- Vectors: `source_control.json` through `RunOwned("authority")` over
  the KV encoding → `sources.State` → `Follower.Apply` → `Query` path.
- Integration: SC-08 steps 2, 3, 6, 7, 8 as written (the alert-clearing
  parts are WP-12's); a switch with NATS KV unreachable is refused with
  503 and nothing is written; version monotonic within an epoch, a new
  epoch accepted at any version; the 60 s republish repairs a deleted
  key; a follower started with KV down starts enabled and logs it.
- E-10: KV value and message size bounds; a `State` with more controls
  than fit is refused by the API with the limit named.
