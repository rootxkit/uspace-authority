# WP-24: staging deployment and the cutover

Branch `feat/WP-24-deploy-staging`. Milestone A-M5. Owns `deploy/*`
(beyond WP-0's dev compose), the `image` CI job's signing and SBOM, the
backup and restore scripts, the Caddy snippet and the cutover runbook.
Depends on WP-13 (something to show) and WP-21 (the web image); every
other process joins as it lands. Consumers: the lab (`make demo`, load
tests against the published images), A-M5.

## What to build

- `deploy/compose.yaml`: the seven Go services from one image with
  their entrypoint arguments, the one-shot `migrate` service (same
  image, `migrate` subcommand, both trees; the long-running services
  `depends_on` it with `condition: service_completed_successfully` and
  refuse to start on a lower schema version, D7, M36), `web`, **one
  `timescale/timescaledb-ha:pg16` container** holding both databases
  (`authority_relational` with PostGIS, `authority_timeseries` with
  TimescaleDB; separate databases, trees and version tables; M37),
  `nats` (JetStream, file store, per-process credentials generated by a
  script into a git-ignored directory), named volumes (databases, NATS,
  ground tiles, evidence) and the shared read-only basemap volume the
  deployment repo provides (M38), health checks, restart policies,
  resource limits sized for the demo droplet (plan §10 budget; the
  droplet itself is Q-A20), an isolated network; only Caddy's network
  joins `api`, `picture-ws`, `rid-ingest`, `dp-poller` (for `/uss/*`)
  and `web`. The dev compose (`compose.dev.yaml`) keeps the same single
  container so local and staging never differ in layout.
- `deploy/caddy/authority.snippet`: this system's Caddy *snippet* (path
  routing of plan §10; `client_auth { mode verify_if_given }` on the
  mTLS routes with `X-Client-Cert-Subject` forwarded there and stripped
  everywhere else; `/basemap/*` as a `file_server` on the shared volume
  with range requests and long cache headers). The private deployment
  repo `uspace-deploy` (its WP-D1) composes the five systems' snippets
  into the one Caddyfile and owns the mTLS CA tooling; `deploy/staging/`
  holds only what names the staging host. `AUTHORITY_MTLS_MODE=off` on
  staging (M25).
- `deploy/.env.example` per service group with every variable
  documented; secrets come from the private infra repo's environment.
- Image job: build on `main` and tags, push to GHCR with `sha-<short>`
  and `v*` tags, cosign keyless signing, SBOM (syft) attached;
  `deploy/verify-image.sh` checks the signature before `compose pull`.
- `deploy/deploy.sh`: pull, verify, run the `migrate` service and read
  its exit status and the version it reports, rolling restart in
  dependency order, then **verify** `/readyz` of every service and the
  status line of each, and print what was verified; exits non-zero and
  says which check failed (E-02). `web` is built with `pnpm` in CI
  (`--frozen-lockfile`), never on the server.
- Backups: nightly `pg_dump` of both databases and the NATS KV export
  to the droplet and an off-droplet copy; `deploy/restore-check.sh`
  restores last night's dumps into scratch databases, counts rows in
  `events`, `uas_operators` and `rid_observations`, and prints the
  counts (never "ok" without numbers).
- Cutover runbook `docs/runbooks/cutover.md`: the order in which
  `utm.chikox.net` and `ingest.chikox.net` are retired, what moves
  (registry export → WP-20 import; receivers re-keyed to the F9
  contract), the rollback (the old stack stays stopped but intact for a
  week), and the A-M5 checklist.
- Resource measurement: RSS and CPU per service at the lab's 100-drone
  profile recorded in the runbook.

## Tests

- `docker compose config` validated in CI; `compose up` smoke in CI
  with the published image (`migrate` completes and prints both
  versions; a process started against an older schema refuses and
  names the version, E-01; health of every service, `/readyz`, one
  receiver batch accepted, one picture frame received).
- `restore-check.sh` run in CI against a dump taken in the same job
  (E-01: a dump with known counts).
